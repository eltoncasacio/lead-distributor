## O que foi construído (SQL)

Arquivos em [`sql/comandos_whatsapp/`](../../sql/comandos_whatsapp/):

- `FIX_comandos_whatsapp.sql` — funções `normalizar_nome`, `somente_digitos`, `normalizar_telefone_br`, `chave_telefone`, `formatar_telefone`, `_cmd_resp`, **`executar_comando(loja_id, remetente, texto)`**, e os índices `uq_vendedores_loja_nome` e `uq_vendedores_loja_telefone`.
- `ROLLBACK_comandos_whatsapp.sql` — desfaz tudo sem tocar em dados.
- `teste_schema_producao.sql` (schema das 5 tabelas **gerado do catálogo real de produção** em 10/10) e `teste_comandos_whatsapp.sql` — testes.

**O que a função faz:** recebe o texto, descobre o papel pelo número (gerente ou vendedor), executa e devolve `{papel, acao, resposta}`. O n8n só deve repassar a mensagem e enviar o campo `resposta` de volta.

| Comando | Quem | Observação |
|---|---|---|
| `menu` | todos | |
| `meus leads`, `leads`, `status` | vendedor | só o que é dele |
| `status`, `leads` | gerente | a função devolve `acao: legado`; o n8n segue no caminho antigo |
| `listar vendedores` | gerente | |
| `inserir vendedor Nome 19 99999-8888` | gerente | nome e telefone obrigatórios |
| `pausar Nome` / `reativar Nome` (alias `despausar`) | gerente | `pausar` → `inativo` |
| `excluir vendedor Nome` | gerente | status `removido`, histórico mantido |

**Regras de segurança:** só gerente escreve; escrita só por eco-e-reenvio (o sistema responde com o comando pronto, `confirmar ...` + telefone completo, e o reenvio executa); nome único por loja sem regex (`João`=`Joao`=`JOÃO`); telefone único entre vendedores não removidos; telefone digitado precisa conferir com o cadastro; o último vendedor ativo não pode ser pausado nem removido; `anon`/`authenticated` não executam.

**Como rodar os testes** (usa Docker; a imagem `postgres:17` já existe na máquina do dono):

```bash
cd sql/comandos_whatsapp
docker run -d --rm --name lead-sql-teste -e POSTGRES_PASSWORD=x postgres:17 && sleep 6
for f in teste_schema_producao.sql FIX_comandos_whatsapp.sql teste_comandos_whatsapp.sql; do
  docker exec -i lead-sql-teste psql -U postgres -v ON_ERROR_STOP=1 -q -t -A < $f; done
docker rm -f lead-sql-teste
```

## Armadilhas e acessos

- **Credenciais não ficam em arquivo do repositório.** Supabase: `.env` (`SUPABASE_URL`, `SUPABASE_SERVICE_KEY`). n8n: chave da API pública em `N8N_API_KEY` no `.env`, **separada** da do MCP (o MCP só lê workflow). Evolution: a chave **da instância** está em `lojas.evolution_api_key` e basta para consultar estado e reconectar; a **chave global** foi esquecida pelo dono e não é necessária para isso.
- **Reconectar a Evolution** sem a chave global: `GET https://evolution.yavoh.cloud/instance/connect/renato-motors?number=<numero_da_loja>` com o header `apikey` da instância devolve um `pairingCode` de 8 caracteres, que o dono digita no WhatsApp ("Conectar com número de telefone"). Expira em ~1 minuto.
- **Verificar conexão (leitura):** `GET /instance/connectionState/renato-motors`. Estado `close` com `statusReason: 401` = sessão desligada do aparelho.
- **`execute_workflow` do MCP dispara o workflow de produção de verdade.** Não usar para testar.
- **Executar o `FIX` de novo é seguro** (`CREATE OR REPLACE`, índices `IF NOT EXISTS`).
- **`reativar` aceita vendedor `removido`** — diverge da documentação, que trata `removido` como definitivo na UI. Foi proposital (caso do Japa).
- **O índice de nome único vale também para o Dashboard.** Duplicar nome por lá passa a mostrar o erro bruto do banco.
- **Quem manda a mensagem de comando é o gerente para o número da loja.** O `loja_id` vem da instância, não do que o usuário digita — é isso que isola as lojas.
